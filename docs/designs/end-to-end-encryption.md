# Design: End-to-end encryption with libsignal (PQXDH + Double Ratchet)

Generated by /office-hours on 2026-10-04
Branch: main
Repo: Siddhesh-source/whispr
Status: APPROVED
Mode: Builder

## Problem Statement

Today the server stores message payloads (text, read receipts, contact
requests) as plaintext until they are delivered (docs/THREAT_MODEL.md:136,
"Phase 2 gap"). The goal is that the server can no longer read any message
content. Outgoing payloads are encrypted with libsignal sessions (PQXDH, then
the Double Ratchet). The server only relays ciphertext and hands out public
prekeys.

The user's brief, verbatim:

> Goal: the server can no longer read any message content.
> 1. Session setup with libsignal: PQXDH key agreement, then Double Ratchet.
> 2. Client keys: signed prekey, one-time prekeys, and post-quantum prekeys. Upload them, replenish them when low, and rotate the signed prekey on a schedule.
> 3. Server: prekey bundle endpoints. Each one-time prekey is handed out once, atomically, and requests are rate limited.
> 4. Implement libsignal's storage interfaces (sessions, prekeys, identities) on the local database. Encrypt that database with SQLCipher using a Keystore-protected key.
> 5. Encrypt the whole payload: text, replies, reactions, and receipts.
> 6. Handle the hard cases: first message to an offline user, out-of-order and duplicate messages, decryption failure with a session reset, and identity key changes (reuse the Phase 3 warning).
> 7. Update docs/THREAT_MODEL.md to state exactly what the server can still see.
>
> Done when:
> - Tests prove that a database dump and a captured network session contain no plaintext.
> - Replayed and tampered messages are rejected.
> - Messaging from Phase 2 behaves the same for the user, including offline delivery.

## What Makes This Cool

- The "not end-to-end encrypted yet" banner in every chat goes away
  (`chat_not_encrypted` in strings.xml), and it becomes true that the server
  operator cannot read messages.
- It is post-quantum from day one. libsignal 0.104's `PreKeyBundle`
  *requires* a Kyber prekey (constructor checked with javap), so there is no
  classical-only fallback to ship by accident.
- Phase 3's trust work pays off: the key pinned from a QR scan becomes the
  identity that libsignal checks on every session.

## Constraints

- **Crypto:** libsignal only, no custom cryptography.
  - Padding is framing, not crypto: 0x80, then zeros up to a multiple of 160
    bytes. It is applied before `SessionCipher.encrypt` and stripped after
    decrypt.
- **Server:** payloads stay opaque. No key material or content is logged.
- **Phase 2 invariants that must hold:**
  - The device acks an envelope only after its DB commit.
  - Delivery is exactly-once by message ID.
  - Messages to one peer are sent in order.
  - Offline sending goes through the persistent outbox.
  - Pushes are content-free wake-ups.
- **Reused infrastructure:**
  - Android: Room + SQLCipher (Keystore-wrapped key) and the existing
    identity key file `identity.v1.bin` (Keystore-wrapped).
  - Server: signature checks use the existing `sigverify` FFI.
- **libsignal 0.104 store contracts (checked with javap):**
  - `IdentityKeyStore.saveIdentity` returns `IdentityChange`.
  - `KyberPreKeyStore.markKyberPreKeyUsed(kyberId, signedId, baseKey)` throws
    `ReusedBaseKeyException`, so the store must remember base keys used with
    last-resort Kyber keys.
  - The callbacks are synchronous.

## Premises (agreed)

1. One device per account (libsignal deviceId 1). Multi-device is out of
   scope.
2. The server is crypto-free. It stores and hands out prekeys and verifies
   their signatures with the existing libsignal FFI verifier. It never sees
   sessions.
3. The scope is content. Metadata (who talks to whom, and when) stays visible,
   and sealed sender is out of scope. Plaintext is padded so that ciphertext
   length doesn't reveal exact message length.
4. This is a dev build, so there is no migration.
   - Undelivered plaintext envelopes are purged on upgrade.
   - From then on, clients reject any message envelope that isn't libsignal
     ciphertext. Otherwise the server could inject fake plaintext.
5. Encryption wraps the whole `Payload` generically.
   - Replies and reactions don't exist yet (`Payload.kt` has text, read,
     contact_request and typing).
   - They will be encrypted automatically when they are built. Building them
     is a separate feature.
6. "Database dump" means both the server's Postgres and the device's SQLCipher
   file. The device test is extended to cover the new session and prekey
   tables.

## Approaches Considered

### Approach A: Minimal, encrypt on send
This is the same send path as B: encrypt the outbox head once and persist the
ciphertext. A decryption failure shows a visible "couldn't decrypt"
placeholder but never recovers the content.

Rejected: an unrecoverable message is a user-visible change from Phase 2,
which fails "behaves the same". B is A plus a recovery protocol.

### Approach B: Encrypt on send, plus a recovery protocol (CHOSEN)
See Recommended Approach.

### Approach C: Build the session when the contact is added, encrypt at enqueue
Rejected:
- After a reset, every queued ciphertext belongs to a dead session.
- The ratchet advances at enqueue time.
- It still needs B's recovery protocol.

## Recommended Approach (B)

### Wire format (inside the opaque envelope payload)

```
payload   := 0x01 (format v1) | type | libsignal serialized message
type      := 0x01 PreKeySignalMessage | 0x02 SignalMessage
plaintext := pad160( PayloadCodec.encode(payload) )   // before encryption
```

- The engine first branches on the envelope's `kind`.
  - `delivered`: server-generated, empty payload, no content. It is handled
    as today and never checked for a format byte.
  - Message-kind envelope: its payload must start with 0x01 and a known type.
    Otherwise it is acknowledged and dropped.

### Payload model changes (PayloadCodec, JSON discriminator `t`)

| Variant / field | Encoding | Meaning |
|---|---|---|
| `Text.mid` | `"mid": uuid string` | Logical message ID. Equals the transport ID on first send. |
| `Text.ts` | `"ts": epoch ms` | Original send time. A resend keeps it, so the swapped message sorts correctly. |
| `replaces` on `Text`, `Read`, `ContactRequest` | `"replaces": transport id, optional` | Set only on an auto-resend. Names the failed transport ID whose placeholder it resolves. |
| `SessionReset` (`t:"reset"`) | `{"failed":[transport ids]}` | "I couldn't decrypt these from you; resend them." |
| `ResetDone` (`t:"reset_done"`) | `{"resent":[ids],"control":[ids],"lost":[ids]}` | The sender's answer to a reset: which IDs it resent, which were control messages (delete their placeholders silently), and which can't be recovered. |
| `ContactRequest`, `Read`, `Typing` | otherwise unchanged | |

**IDs on outgoing messages.** An outgoing message row's UUID is its `mid`, and
also its first transport ID.
- Delivered receipts (which reference a transport ID) are resolved to a `mid`
  through `sent_envelopes`.
- Read receipts list `mid`s.

So a resent message still moves Sent → Delivered → Read.

Old codecs already return null for unknown variants
(`PayloadCodec.decode`), and the engine acks and drops those. This is a dev
build, so mixed versions are not supported anyway.

### Identifiers and dedup are scoped by sender

- The envelope `id` is a **transport ID**. The server dedups on
  `(sender, id)` and keeps tombstones for 30 days. A resend therefore always
  gets a new transport ID.
- Device tables key every sender-chosen ID on `(sender, id)`:
  - `seen_envelopes(senderId, transportId, receivedAt)` is checked before
    decryption. It is purged after 30 days.
  - `messages` gets a unique index on `(peerId, messageId)` (replacing
    `messageId` alone) with `messageId = mid` for incoming. Outgoing rows keep
    their locally generated UUID.
  - Placeholders and `replaces` resolution match on `(sender, transportId)`.
    A replacement only counts if it comes from the same sender as the
    placeholder.

### Server (Go)

- **Migration `0004_prekeys`:**
  - `users.registration_id INT NULL`.
  - `signed_prekeys`: one current row per user.
  - `kyber_last_resort`: one current row per user.
  - `one_time_prekeys`, `kyber_prekeys`: many per user, PK `(user_id, key_id)`.
  - `DELETE FROM envelopes`, to purge stored plaintext.
  - Every table uses `ON DELETE CASCADE` from `users`.
- **`PUT /v1/keys`:** uploads the registration ID, signed prekey, last-resort
  Kyber key, and batches of one-time keys.
  - Every signature is verified against the uploader's identity key with
    `sigverify.Verify`.
  - EC keys must be 33 bytes and pass `ValidatePublicKey`. Kyber1024 public
    keys must be 1569 bytes.
  - At most 100 keys per batch, and at most 200 stored per type.
  - Re-uploading a byte-identical key under an existing ID is a no-op.
    A *different* key under an existing ID is rejected with
    `409 key_id_conflict`.
- **`GET /v1/keys/count`:** returns the counts plus the current signed and
  last-resort key IDs.
- **`GET /v1/keys/{userId}`:** returns a prekey bundle.
  - In one transaction it pops one EC one-time key (if any), and one Kyber
    one-time key, falling back to the last-resort key. Each pop is
    `DELETE … WHERE (user_id,key_id) = (SELECT … FOR UPDATE SKIP LOCKED LIMIT 1) RETURNING …`.
  - Returns `404 no_keys` if the user has never uploaded keys.
  - Refuses a request for the caller's own ID.
  - Rate limited per authenticated user, through a new keyed variant of
    `httpx.RateLimiter`. Limits are settled in the eng review.
- **Logging:** the redactor deny-list gains `signature`, `public_key` and
  `prekey`.

### Android `data` module

**`SignalStore`** implements `IdentityKeyStore`, `SessionStore`,
`PreKeyStore`, `SignedPreKeyStore` and `KyberPreKeyStore`.
- **Tables:** new Room tables in the same SQLCipher DB (DB v4):
  - `signal_sessions`
  - `signal_prekeys`
  - `signal_signed_prekeys`
  - `signal_kyber_prekeys` (with a `lastResort` flag)
  - `signal_kyber_used_base_keys`
- **Key IDs:** allocated from monotonic counters persisted in `settings`, so a
  key ID is never reused.
- **Identity key pair:** comes from `LibsignalIdentityRepository`.
- **Registration ID:** stored in `settings`.
- No `SenderKeyStore` is needed: the separate-store constructors of
  `SessionBuilder` and `SessionCipher` are used.

**Identity store semantics** (backed by `contacts`):
- `getIdentity(peer)` returns the pinned `contacts.identityKey`, or null if
  there is no row or the key is empty.
- `isTrustedIdentity(peer, key, SENDING)` is true only if:
  - the key equals the pinned key and trust is not `KeyChanged`, or
  - nothing is pinned yet (TOFU, matching today's `ensureContact`).
- `isTrustedIdentity(peer, key, RECEIVING)` is always true. **Interim policy,
  revisitable in eng review (Open Question 1):** decrypt, and if the key
  differs from the pin, mark the contact `KeyChanged`. This is Signal's
  behaviour and reuses the Phase 3 warning, which blocks sending until the
  user acknowledges.
- `saveIdentity(peer, key)` runs inside the decrypt transaction:
  - **No contact row:** insert one as a request (`isRequest = true`,
    `identityKey = key`, name "Unknown contact" until the server lookup or the
    contact request fills it in).
  - **Empty pin:** pin the key.
  - **Different from the pin:** `flagKeyChange` (the pin stays; the new key is
    held as `pendingKey`).
  - It returns `NEW_OR_UNCHANGED` / `REPLACED_EXISTING` accordingly.

**`SessionCrypto`** wraps `SessionBuilder` and `SessionCipher`.
- **Threading:** all crypto runs on a single-threaded crypto dispatcher.
  State changes run inside `db.runInTransaction`. **Network I/O never runs
  inside a transaction.**
- `encrypt(peer, payload)`:
  1. If no session exists, fetch the bundle *outside* any transaction.
  2. Open a transaction. Re-check that no session appeared in the meantime.
     If so, discard the bundle.
  3. Otherwise check the bundle's identity key against the pin (see "Send
     path") and `SessionBuilder.process` it.
  4. Pad and encrypt, and persist the ciphertext to the outbox row in the
     same transaction.
- `decrypt(sender, bytes) { plaintext -> work }`: decryption, the store's
  session writes and `work` all commit in one transaction. `work` covers
  inserting the message, applying a receipt, and so on.

**`PreKeyMaintainer`** runs on every connection open:
- **Registration:** registers if needed (registration ID, signed prekey,
  last-resort Kyber key).
- **Top-up:** when the server count drops below 20, tops up to 100 EC and 100
  Kyber one-time keys.
- **Rotation:** rotates the signed and last-resort keys every 7 days.
- **Retention:** keeps old private keys for 30 days (the server's envelope
  retention), then deletes them. Deleting a last-resort key also deletes its
  `signal_kyber_used_base_keys` rows.
- **Not pruned:** private one-time keys whose public half was popped but never
  used in a message. In this build they grow without bound; the bundle-fetch
  rate limit only caps how fast. Pruning them is a TODO.

### Send path (outbox)

- **Per-recipient lanes.** The outbox stays one persisted queue, and the pump
  still has one envelope in flight.
  - The head is the oldest entry whose recipient isn't **parked**. A blocked
    recipient therefore never stalls other chats.
  - Entries for the same recipient stay strictly in order behind their parked
    head, so per-conversation order is preserved.
  - New column `outbox.ciphertext BLOB NULL`: the pump encrypts once and
    resends byte-identical bytes.
- **Parking.** A recipient is parked (`parked_recipients(recipientId, reason,
  retryAt)`) when:
  - The server returns `no_keys` (peer never registered). Retry with backoff.
    The message shows "Sending", as Phase 2 shows for an offline recipient.
    It is delivered once the peer registers keys.
  - A network error occurs while fetching the bundle. Retry with backoff.
  - The bundle's identity key differs from the pin. The contact is flagged
    `KeyChanged` (`pendingKey` = bundle key) and the Phase 3 warning appears.
    The lane stays parked until the user acknowledges; then it unparks and
    builds a session against the acknowledged key.
  - `SessionCipher.encrypt` throws `UntrustedIdentityException`. This happens
    when an incoming message flagged the contact `KeyChanged` while a session
    already existed. The lane is parked with reason KeyChanged.
- **Acknowledging a key change:**
  - The pin is replaced by `pendingKey`, trust resets to Unverified, and the
    lane unparks.
  - If the existing session's remote identity equals the new pin, it is
    reused. This is the usual case after an incoming key change.
  - Otherwise the session is deleted, and the next send rebuilds it from a
    fresh bundle.
- **No pinned key** (empty `identityKey`): the bundle key is pinned (TOFU), as
  `ensureContact` does today.
- **Sent-envelope log.** `sent_envelopes(recipientId, transportId, mid, kind,
  padded plaintext, sentAt, autoResent BOOLEAN)` is written in the same
  transaction as the encryption and kept for 30 days. It is what a reset
  resends from. This is device-only data inside SQLCipher; the same text
  already lives in `messages.body`.
  - Control payloads (`SessionReset`, `ResetDone`) are logged with
    `kind = control` and no plaintext, so a reset that names them can answer
    "control" rather than "lost".

### Receive path

1. **Classify.** `kind = delivered` is handled as today. Otherwise:
2. **Dedup.** If `(sender, transportId)` is in `seen_envelopes`, ack and stop.
   This covers a replay with the same ID.
3. **Decrypt and store.** In one transaction: decrypt, run `work`, and insert
   into `seen_envelopes`. Then ack.
4. **Errors:**
   - `DuplicateMessageException`, or `ReusedBaseKeyException` (a PreKey
     message replayed against a last-resort Kyber key): treat it as a replay.
     Record it as seen, ack, drop.
   - Any other unexpected exception (for example a DB error): **don't ack**.
     The connection drops and the envelope is redelivered, which keeps
     ack-after-commit.
     - The same transport ID failing like this 3 times in one process is
       treated as a decrypt failure (below), so one poison envelope can't
       block the queue.
   - A transient frame (typing) that fails to decrypt is dropped silently:
     no placeholder and no reset.
   - Bad format, `InvalidMessage`, `InvalidKey`, `InvalidKeyId`, `NoSession`
     or `InvalidVersion`: in **one transaction before the ack**:
     - insert a placeholder message ("Couldn't decrypt. Asked the sender to
       resend."), keyed by `(sender, transportId)`;
     - mark it seen;
     - insert `pending_resets(peerId, transportId, state = queued,
       attempts = 0)`.

     Then ack.

### Session reset (durable, coalesced, sender-scoped, bounded)

**Receiver side**
- `pending_resets` has one row per failed ID. The worker and the receive path
  both run on the single crypto dispatcher, so they never interleave.
- The worker runs on connect and whenever a row becomes due, at most once per
  peer per 5 minutes. Failures during the cooldown add more `queued` rows, so
  the next reset carries all of them.
- To reset, the worker:
  1. archives the session;
  2. fetches the peer's bundle outside a transaction, applying the send-path
     identity rules;
  3. in **one transaction**, enqueues an encrypted `SessionReset(failed =
     exactly the queued IDs it read)` through the outbox, and moves *those
     rows only* to `awaiting` with `attempts + 1`. IDs that arrive later stay
     `queued` for the next reset.
- On a network error the rows stay `queued` and are retried with backoff.
- **When an ID is resolved**, by a payload with a matching `replaces` or a
  `ResetDone` naming it, its row is deleted and its placeholder is updated.
- **Rows still `awaiting` 24 hours after the reset** go back to `queued`. The
  reset is re-sent from this table, not from `sent_envelopes`, so a reset
  that itself failed to decrypt is retried.
- **After 3 attempts** the row is deleted and the placeholder is finalised as
  "This message couldn't be recovered." This bounds the reset loop.

**Sender side, on receiving `SessionReset(failed)` from P**
- For each listed ID, look up `sent_envelopes` **where `recipientId = P`**.
  IDs that weren't sent to P are ignored.
- Rows with `autoResent = false` and a content kind (text, contact_request,
  read) are re-encrypted from their stored padded plaintext under a new
  transport ID and enqueued with `replaces = failedId`.
  - The original row gets `autoResent = true`.
  - The resend is logged with `autoResent = true`, so a message is
    auto-resent **at most once**.
  - Because read receipts are recovered too, the sender's status still
    reaches Read.
- The sender then enqueues one `ResetDone` that classifies every listed ID
  (resent, control, or lost). Lost covers IDs that were already auto-resent,
  have expired from the log, or were never sent to P.
- Typing payloads are never logged.

**Placement on the receiver**
- A `Text` with `replaces` updates the placeholder row in place. It keeps the
  placeholder's `localOrder` and uses the original `ts` as its timestamp, so
  it appears where the lost message was.
- A `Read` or `ContactRequest` with `replaces` is applied normally, and its
  placeholder is **deleted**. A recovered contact request moves the contact to
  Requests as usual.
- `ResetDone.control` IDs: placeholders deleted silently.
- `ResetDone.lost` IDs: placeholders finalised as "This message couldn't be
  recovered."
- A tampered or injected envelope with no matching sent row therefore ends in
  that final state, not in a permanent "asked to resend".
- If no placeholder exists, the payload is inserted normally (mid dedup still
  applies).

**Contact requests from strangers**
- The first PreKey message creates the request contact row via
  `saveIdentity`.
- If that very first message fails to decrypt, the placeholder lands in
  Requests under a contact row made from the server lookup (TOFU), and the
  reset fetches that peer's bundle.
- `ContactRequest.key` is cross-checked against the PreKey identity. A
  mismatch → `flagKeyChange`.

**Typing indicators**
- These are encrypted too, but only sent when a session already exists.
  They never fetch bundles or consume one-time prekeys.

## Success Criteria

**JVM tests** (Robolectric, real libsignal, FakeGateway recording every frame
and HTTP body):
- Alice→Bob text, read receipt, typing and contact request all arrive, and a
  marker string never appears in any recorded byte.
- Sessions survive an app restart (reopened DB).
- **Replay and tamper:**
  - A replay with the same ID is dropped.
  - Replaying the same ciphertext under a new ID is dropped
    (`DuplicateMessageException`).
  - A bit-flipped ciphertext is rejected. A placeholder is shown, the reset
    is sent, and the message is auto-resent once and replaces the
    placeholder in place.
  - A lost read receipt is recovered by the reset, leaves no placeholder
    behind, and the original message reaches Read.
  - A resent text reaches Delivered and Read on the sender.
  - A tampered envelope with no matching sent row → `ResetDone.lost` →
    placeholder finalised as "couldn't be recovered".
  - A `SessionReset` that itself fails to decrypt → retried from
    `pending_resets` after 24 h, then finalised after 3 attempts.
  - A failure arriving while a reset is being sent stays queued and goes out
    in the next reset.
  - A PreKey message replayed under a new ID against the last-resort key
    (`ReusedBaseKeyException`) → dropped with no reset.
  - A failed typing frame produces no placeholder.
- **Reset hardening:**
  - Three failures inside one cooldown window → one reset carrying all three
    IDs.
  - A reset listing IDs that were sent to a *different* contact resends
    nothing.
  - A second reset for the same ID doesn't resend it again.
  - A process kill between the ack and the reset still sends the reset after
    restart.
- **Sender scoping:** two senders using the same transport ID and the same
  mid both get their messages delivered.
- **Identity:**
  - A bundle whose key differs from the pin → contact KeyChanged and that lane
    parked, while another contact's messages still go out.
  - A `ContactRequest.key` that differs from the PreKey identity → flagged.
  - Incoming from a changed key → decrypted and flagged (interim policy).
    A message already queued to that contact is parked (KeyChanged) and goes
    out after the user acknowledges, reusing the session.
- **Offline:**
  - A first message to a peer who has no keys yet stays "Sending", doesn't
    block other chats, and is delivered after the peer registers.
  - A message typed while the sender is offline is delivered on reconnect.

**Go tests:**
- 50 concurrent bundle fetches never hand out the same one-time key twice.
- The last-resort key is used after one-time keys are exhausted.
- Bad signatures, wrong lengths, and key-ID conflicts (409) are rejected.
- The keyed rate limit is enforced.

## Reviewer Concerns

Disposition: CONCERNS_RECORDED

Stop: MAX_ITERATIONS

### R3-1 — consistency

**Problem**

> Receive path step 4 drops 'a transient frame (typing) that fails to decrypt' with no placeholder and no reset. To do that, the receiver must tell a typing frame apart before it decrypts, so the frame type (or a separate transient route) is visible outside the ciphertext, and therefore to the server. Yet the Docs section says typing is 'no longer visible' to the server and leaves typing out of the server-visible list. Typing is also defined only as a variant inside the encrypted Payload. The test 'A failed typing frame produces no placeholder' cannot pass unless one of these changes.

**Remedy**

> Choose one. (a) Keep a visible transient/typing envelope kind that the server relays without storing, and list 'typing activity and its timing' in THREAT_MODEL.md's server-visible list. Or (b) keep typing opaque and define that a failed typing frame is handled like any other failure, ending via ResetDone.control or lost. Then align the receive path, the Docs list and the test.

### R3-2 — completeness

**Problem**

> 'When an ID is resolved' says a ResetDone naming an ID deletes its pending_resets row and 'updates' its placeholder. Only the control case (delete) and the lost case (finalise) are defined. Nothing defines what happens for ResetDone.resent IDs. If the resend itself fails to decrypt, or is still in flight, the original row is already deleted. Its placeholder then stays 'Asked the sender to resend' with no terminal state, because no timeout or attempt bound applies once the row is gone.

**Remedy**

> Specify that ResetDone.resent does not resolve the row. The row stays awaiting until the payload with the matching `replaces` arrives, and the timeout, attempt bound and finalisation still apply.

### R3-3 — clarity

**Problem**

> If an auto-resend fails to decrypt at the receiver, its `replaces` field is inside the ciphertext. The receiver therefore creates a second placeholder for the resend's transport ID and resets it, and the sender answers 'lost' because the resend is logged with autoResent = true. The user ends up with two bubbles for one message, and the document does not say whether this is intended.

**Remedy**

> Have ResetDone report, for a lost resend ID, the original ID it replaced, so the receiver deletes the duplicate placeholder and finalises only the original. Or state that the duplicate bubble is accepted. Add a test in which the auto-resend itself fails to decrypt.

### R3-4 — completeness

**Problem**

> Resolution has no state guard. ResetDone.lost 'finalises' placeholders and a `replaces` payload 'updates the placeholder row in place', but nothing defines what happens when these arrive out of order or more than once. A later or duplicate ResetDone listing an ID as lost could overwrite a row already recovered as real text. This follows from the timed retry: by then the ID is already autoResent, so the sender reports it as lost. A `replaces` arriving after finalisation, or after the pending_resets row was deleted, also has no defined behaviour.

**Remedy**

> Specify a monotonic placeholder state machine (pending -> recovered | unrecoverable). `lost` applies only to rows that are still pending, `replaces` recovers a row from pending or unrecoverable, and any resolution for an ID that is already resolved is ignored. Add tests for ResetDone(lost) arriving after a successful resend and for a resend arriving after finalisation.

### R3-5 — feasibility

**Problem**

> The re-queue from awaiting to queued runs on the receiver's wall clock: 24 h per attempt, then finalised after 3 attempts. A sender who is simply offline for 2-3 days has every failed message finalised as 'couldn't be recovered' even though nothing went wrong. On reconnect the sender processes all the queued resets: the first one triggers a real resend, and the later ones report the same ID as lost. The bound confuses 'not answered yet' with 'reset lost'.

**Remedy**

> Base retries on evidence that the reset was not received. For example, measure the timeout from the server `delivered` receipt for the reset's transport ID, or re-send only when delivered arrived and no ResetDone followed. Otherwise, state the accepted behaviour for long-offline senders. Add a test where the sender is offline for longer than the retry window.

### R3-6 — clarity

**Problem**

> The attempt bound is ambiguous. 'After 3 attempts the row is deleted and the placeholder is finalised' can mean finalising as soon as the third reset is enqueued, which gives that reset no chance to be answered. It can also mean finalising when the third awaiting window expires. The test wording ('retried ... after 24 h, then finalised after 3 attempts') doesn't settle it.

**Remedy**

> State the exact transition: for example, finalise when a row is awaiting with attempts = 3 and its window expires without resolution. Make the test assert that transition.

### R3-7 — clarity

**Problem**

> The send path says the pump 'encrypts once' at the lane head, and Approach C was rejected because 'the ratchet advances at enqueue time'. But the reset worker 'enqueues an encrypted SessionReset', and the sender side re-encrypts resends and then enqueues them. It is unclear whether SessionReset, auto-resends and ResetDone are encrypted at enqueue time or by the pump at the head. Encrypting at enqueue reintroduces the enqueue-time ratchet advance that was rejected, and puts these messages ahead of earlier unencrypted entries in the same lane. The point at which their sent_envelopes rows are written is also undefined.

**Remedy**

> State that these payloads are enqueued as plaintext (resends carry the stored padded plaintext) and encrypted by the pump at the head. Their sent_envelopes rows are then written in that encryption transaction. If they must be encrypted at enqueue instead, justify that and define how they order against earlier entries in the lane.

### R3-8 — completeness

**Problem**

> The reset worker fetches the bundle 'applying the send-path identity rules', but the document doesn't say what happens to pending_resets rows when those rules park the lane: a bundle key that differs from the pin, `no_keys` (for example the peer reinstalled), or repeated network errors. Rows stay queued, and attempts and the 24 h clock only advance once a reset is enqueued. So while a key-change warning sits unacknowledged, placeholders read 'Asked the sender to resend' although no reset was sent, and the attempt bound never triggers. The session was also already archived in step 1, before a usable bundle was obtained.

**Remedy**

> Define reset behaviour while the lane is parked. For example, rows wait for the lane to unpark and the placeholder text reflects that, or rows are finalised after a stated parked duration. Decide whether the session is archived only after a usable bundle is obtained. Add a test for a reset to a contact whose bundle key changed.

### R3-9 — feasibility

**Problem**

> The poison-envelope guard counts 3 failures of the same transport ID 'in one process'. An envelope whose processing crashes the process, or one being retried while Android routinely kills the app, resets this in-memory counter on every restart. It can then block that sender's queue indefinitely, which contradicts 'one poison envelope can't block the queue'.

**Remedy**

> Persist the failure counter, for example in a table keyed by (sender, transportId) and written outside the failing transaction, or document the crash case as an accepted limitation. Add a test showing that a restart does not reset the count.

### R3-10 — completeness

**Problem**

> A PreKey message can be replayed under a new transport ID after its session is gone: the session was deleted when a key change was acknowledged, aged out of the archived states, or seen_envelopes was purged after 30 days. In that case libsignal throws InvalidKeyId (the one-time key was consumed) or InvalidMessage. Both map to decrypt failure, so the replay produces a visible placeholder and a reset, and ends as a 'couldn't be recovered' bubble. This breaks 'replayed messages are rejected', and the replay tests only cover a live session.

**Remedy**

> Treat InvalidKeyId for a prekey ID that was already consumed or retired as a replay (ack and drop silently). Key IDs are monotonic, so a retired ID can be told apart from an unknown one. Otherwise, document the residual behaviour as accepted. Add a replay test that runs after the session is deleted.

### R3-11 — completeness

**Problem**

> THREAT_MODEL.md is specified to list what the server can see, but not what a malicious server can still do under this design. It can inject undecryptable envelopes under a real sender. Each one creates a visible 'Couldn't decrypt' bubble that ends as 'couldn't be recovered', and forces a reset (at most once per 5 minutes) that archives a healthy session and pops one of the peer's one-time prekeys. It can also withhold or delay envelopes. Brief item 7 asks for exactness.

**Remedy**

> Add the server's remaining active capabilities to THREAT_MODEL.md: injecting fake decrypt-failure bubbles, forcing resets and prekey consumption bounded by the cooldown, and dropping or delaying envelopes. Optionally, avoid archiving an established session after a single InvalidMessage.

### R3-12 — consistency

**Problem**

> Approach A is rejected because 'an unrecoverable message is a user-visible change from Phase 2, which fails "behaves the same"'. B also ends messages as 'This message couldn't be recovered': after 3 attempts, after log expiry, after a failed resend, and for tampered envelopes. B narrows this divergence but does not remove it, so the rejection rationale and the 'behaves the same' criterion overstate what B delivers.

**Remedy**

> Restate the rationale: B recovers the common failure cases, and only tampered, expired or twice-failed messages end as unrecoverable. List that residual divergence explicitly against the 'behaves the same' criterion.
